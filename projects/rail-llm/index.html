Summary of the Paper

This is my understanding of the transformers, attention, and what happens inside it. I read the model Architecture (Section 3 of Attention is All You Need paper avaialble here, referred to as ‘the paper’ going forward in this blog) and viewed the videos by 3Blue1Brown & Andrej Karpathy to nail in my understanding of it.

Video by Andrej Karpathy - Let’s build GPT: from scratch, in code, spelled out.

The transformer has an encoder part as well as a decoder part. But in this project, I’m only interested in the decoder part of the transformer. The steps involved are as follows:

  1. We embed the tokens (text being read is broken into tokens). A token could be a word, a part of a word, a special character, etc. Embedding a token means representing a token in a huge dimension. (Say, 512 as given in the paper. It could be more).
  2. We add a position component for each token. Otherwise the model doesn’t know what token appears where in the string.
  3. Attention Block
  • 3.1 Each token has a query and key vector (\(Q\) and \(K\) respectively) that is obtained by multiplying the \(W_q\) and \(W_k\) respectively with the embedding.
  • 3.2 We take the dot product of the \(Q\) and \(K\) vectors to get a score. If the key of token 1 aligns with the query of token 2, that means the embedding of token 1 “attends” to the embedding of token 2. This results in a large value for the score, essentially meaning token 1 “has something to say about” token 2.
  • 3.3 We divide this by the square root of the dimension of the embedding to prevent the dot product from growing too large.
  • 3.4 We mask the score of future words by setting the value to \(-\infty\). This is done so the model doesn’t “see the answer.” For example, in the string “I read the paper and it was interesting,” once we reach “I read the paper,” we don’t want the model to see the next word. (Note: Masking is not done in an encoder). We use \(-\infty\) because the softmax function will then turn that value into \(0\).
  • 3.5 We apply the softmax function to get the probabilities.
  • 3.6 We calculate the value vector by multiplying the embedding with \(W_v\) (Value weight matrix).
  • 3.7 We calculate the weighted sum of the value vector with the score.
  • 3.8 This is repeated 6 times (according to the original paper), or \(n_{layer}\) times sequentially.
  1. All the elements in the attention block is repeated in parallel in different heads. We use n_heads parameter to determine how many heads we want. All the results from the n_heads heads is concatenated into one vector. This is multiplied by a final weight matrix to fuse them into a single d_k dimensional vector.
  2. Add & Norm Layer
  • 5.1 This result is added to the original embedding to get the modified embedding. This is called the ‘add layer’ or the ‘residual connection’
  • 5.2 To keep the activations within a consistent range, we add a norm layer. It could be RMSNorm
  1. We have a MLP at the next level where each of the embedding vectors is paralelly processed.
  2. We add another Add & Norm layer as described before
  3. We add a last linear layer
  4. Softmax to get the probability

Note: Since I am not talking about the encoder here, I skipped the cross attention part.

Other items

Temperature

This is a parameter you divide the logits by before the softmax in the attention block. \[ \text{Softmax with Temperature} = \frac{e^{\frac{x_i}{T}}}{\Sigma_{n=0}^{N-1}e^\frac{{x_n}}{T}} \]

  • Low Temp (0.1): Makes the highest probability even higher (very focused).
  • High Temp (1.0+): Flattens the distribution (more random/creative).

For FRA manuals, you’ll want a low temperature because you want facts, not “creative” safety rules.

Ingestion

I create a Class called RailDocumentProcessor. I initialize the class using the splitter tool so that the RecursiveCharacterTextSplitter is just called once when an object of the class is initialized (and not for every document). This tool uses parameters chunk_size = 1000, and chunk_overlap = 150. I used chunk_size of 1000 to not lose context of a specific railway rule. Also use an overlap to ensure that any ‘bridge’ between chunks is not lost. Also note: ‘len’ is a built in python function that calculates the length of an object. Say we were using tokens, we would update ‘len’ with ‘tokenizer.len’.

Why use RecursiveCharacterTextSplitter as opposed to CharacterTextSplitter? RecursiveCharacterTextSplitter splits text intelligently by natural boundaries (paragraphs, sentences ,spaces) to keep semantic context intact. CharacterTextSplitter splits simply by a fixed character count, which often breaks words and ruins context.

We use a chunk_size instead of processing the entire document due to context window. LLMs have a limit on how many tokens it can see. The higher the context, the number of parameters that a model has to learn explodes.

This class has the process_directory() method. This goes thru each .pdf file in the directory, extracts texts using the pypdf directory, and then creates chunks and creates chunk using the splitter tool. At the same time it saves metadata for each of the chunk including the source (i.e. the filename), the page number, and the length of character for that chunk.

import pypdf
import os
from langchain_text_splitters import RecursiveCharacterTextSplitter

class RailDocumentProcessor:
    def __init__(self, chunk_size=1000, chunk_overlap=150):
        self.splitter = RecursiveCharacterTextSplitter(
            chunk_size=chunk_size,
            chunk_overlap=chunk_overlap,
            length_function=len
        )

    def process_directory(self, directory_path):
        """Processes all PDFs and returns a tuple: (list_of_chunks, list_of_metadatas)."""
        all_chunks = []
        all_metadatas = []

        if not os.path.exists(directory_path):
            print(f"Error: Directory {directory_path} not found.")
            return [], []

        for filename in os.listdir(directory_path):
            if filename.endswith(".pdf"):
                print(f"Processing: {filename}")
                path = os.path.join(directory_path, filename)
                
                try:
                    reader = pypdf.PdfReader(path)
                    for i, page in enumerate(reader.pages):
                        page_text = page.extract_text()
                        if not page_text:
                            continue
                        
                        # Create chunks for this specific page
                        page_chunks = self.splitter.split_text(page_text)
                        
                        for chunk in page_chunks:
                            all_chunks.append(chunk)
                            # Enhanced metadata for citations and filtering
                            all_metadatas.append({
                                "source": filename,
                                "page": i + 1,
                                "char_count": len(chunk)
                            })
                except Exception as e:
                    print(f"Could not process {filename}: {e}")
                        
        return all_chunks, all_metadatas

For the 5 PDFs, this extracted 2633 chunks. This was surprising to me to see ‘only’ ~3000 chunks. But \[\text{Total Characters} \approx \text{Chunks} \times \text{Chunk Size}\] which gives \[3,000 \times 1,000 = 3,000,000 \text{ characters}\] Even though the 5 PDF files were approximately 25MB, only about 2MB of it is useful text data.

Embedding

The chunks obtained at the end of the ingestion is sent to the embedder. This is available at https://github.com/jac0bmath3w/rail-safety-ai/blob/main/src/embed.py

from sentence_transformers import SentenceTransformer
import torch

class RailEmbedder:
    def __init__(self, model_name='BAAI/bge-base-en-v1.5'):
        # Check if GPU is available
        self.device = 'cuda' if torch.cuda.is_available() else 'cpu'
        print(f"Initializing Embedder on: {self.device}")
        
        self.model = SentenceTransformer(model_name, device=self.device)

    def generate_embeddings(self, text_chunks):
        embeddings = self.model.encode(text_chunks, show_progress_bar=True, convert_to_tensor=False)
        return embeddings

For this purpose, I defined a class called RailEmbedder and initialized with the sentence transformers model called ‘BAAI/bge-base-en-v1.5’. This is available at https://huggingface.co/BAAI/bge-base-en-v1.5. Other options for the sentence transformer model available include: all-mpnet-base-v2, all-MiniLM-L6-v2 (people on the internet say this is dated and not to use it).

This class has a method called generate_embeddings(), which takes as argument the text_chunks. This creates an embedding for each chunk in dimensions. A matrix of size 2633x768 (768 is the dimension of the sentence transform model BAAI/bge-base-en-v1.5) is obtaned as a return value of generate_embedding. If GPU is available, it uses that else it uses CPU (much slower). Earlier, I mentioned that each token has a vector embedding. Each token is approximately 4 characters (source). So why do we have 2633 vectors at the end of generate_embeddings instead of 2633 (chunks) X 250 (1000 chunk_size / 4 charaacter per token) X 768? This is because of pooling. What happens during model.encode is

  1. Tokenizes the chunk into \(N\) tokens.
  2. Generates \(N\) vectors (one for every token).
  3. Collapses those \(N\) vectors into one single vector that represents the average meaning of the whole chunk.

What does convert_to_tensor argument in model.encode() do?

  • convert_to_tensor=True:
    The model returns a PyTorch Tensor. If you are using a GPU, this tensor remains in the VRAM (Video RAM). This is extremely fast if you are immediately passing that data into another neural network layer (like for training).
  • convert_to_tensor=False:
    The model returns a NumPy array. This data is moved from the GPU back to the System RAM (CPU memory). Vector databases (chromadb is used for this project) expects the data in standard format (NumPy). For storage (which is the next step), I want it to be false.

Vector Store

This class acts as the “Librarian” of the system, and handles storage, indexing and retrieval. The embeddings generated by RailEmbedder are stored in the disk using this class. I use chromadb library to store these vectors. I created a class RailVectorVault for this purpose available at https://github.com/jac0bmath3w/rail-safety-ai/blob/main/src/vector_store.py. I pass the embedder_instance of class RailEmbedder and create a collection.

import chromadb

class RailVectorVault:
    def __init__(self, embedder_instance, db_path="./vector_db", collection_name = "rail_safety"):
        # We pass the embedder IN. This is called 'Dependency Injection'.
        self.embedder = embedder_instance 
        self.client = chromadb.PersistentClient(path=db_path)
        self.collection = self.client.get_or_create_collection(name=collection_name)

    def add_documents(self, chunks, metadatas):
        # The Vault asks the Embedder to do its job
        vectors = self.embedder.generate_embeddings(chunks)
        ids = [f"id_{i}" for i in range(len(chunks))]
        
        self.collection.add(
            documents=chunks,
            embeddings=vectors.tolist(),
            metadatas=metadatas,
            ids=ids
        )
    
    def query(self, question, n_results=3):
        """
        Performs a semantic search.
        1. Embeds the question using the injected embedder.
        2. Queries ChromaDB for the closest matches.
        """
        # Embed the query string
        query_vector = self.embedder.generate_embeddings([question])
        
        # Search the collection
        results = self.collection.query(
            query_embeddings=query_vector.tolist(),
            n_results=n_results
        )
        return results

The method add_documents() takes the chunks, embeddings, and the metadata and stores it in drive. The method query 1. Turns the question into a vector. 2. Finds the \(n_results\) most similar chunks. 3. Returns a dictionary containing the text and the metadata.

Phase 2: RAG Pipeline

The Reasoning Engine

I defined the class RailSafetyEngine which serves as the reasoning brain of the RAG system. When you query the vector database, it returns n_results number of text that closely match the embeddings that we stored in the database. Think of it as the librarian returning the relevant books that you need to answer the query. Then the brain processes them to return the answer to the question. I use the following imports from the transformers library

  1. AutoModelForCausalLM
    • A class that loads the correct model architecture based on the model that you pass (example llama or gemma)
  2. AutoTokenizer
    • Handles the translation between human text and numerical values that are fed to a machine.
  3. pipeline
    • Wrapper for the tokenization, model execution, and decoding into one function call.
  4. BitsAndByesConfig
    • This helps to compress the model so that it fits in the T4 GPU memory (used in colab).

When this class is initialzed, the device is mapped (cpu or gpu), the quantization is set up (bnb_config), loads the model (using scaled dot product attention implementation, shortened as sdpa), and creates the pipeline. ‘sdpa’ and 4-bit quantization are the “Optimization Duo” that allows a model meant for a $20,000 server to run on a free Google Colab instance.

from transformers import AutoModelForCausalLM, AutoTokenizer, pipeline, BitsAndBytesConfig
import torch

class RailSafetyEngine:
    def __init__(self, model_id="unsloth/Llama-3.2-3B-Instruct"):
        self.device = "cuda" if torch.cuda.is_available() else "cpu"
        self.tokenizer = AutoTokenizer.from_pretrained(model_id)
        
        # Ensure a padding token exists
        if self.tokenizer.pad_token is None:
            self.tokenizer.pad_token = self.tokenizer.eos_token
        
        bnb_config = BitsAndBytesConfig(
            load_in_4bit=True,
            bnb_4bit_use_double_quant=True,
            bnb_4bit_quant_type="nf4",
            bnb_4bit_compute_dtype=torch.bfloat16
        )
        
        self.model = AutoModelForCausalLM.from_pretrained(
            model_id,
            quantization_config=bnb_config,
            device_map="auto",
            attn_implementation="sdpa"
        )
        
        self.pipe = pipeline(
            "text-generation",
            model=self.model,
            tokenizer=self.tokenizer,
            max_new_tokens=512,
            temperature=0.1, 
            device_map="auto"
        )

    def generate_answer(self, question, context_chunks):
        if not context_chunks:
            return "No relevant safety manual excerpts were found."

        context_text = "\n\n".join(context_chunks)
        
        # 1. Structure the data as a standard list of messages
        messages = [
            {
                "role": "system", 
                "content": "You are a Senior FRA Safety Consultant. Use ONLY the provided context. Cite Page numbers."
            },
            {
                "role": "user", 
                "content": f"CONTEXT:\n{context_text}\n\nQUESTION: {question}"
            }
        ]
        
        # 2. Use the model-agnostic chat template
        # tokenize=False returns a string; add_generation_prompt=True adds the 'assistant' header
        prompt = self.tokenizer.apply_chat_template(
            messages, 
            tokenize=False, 
            add_generation_prompt=True
        )
        
        # 3. Generate
        outputs = self.pipe(
            prompt, 
            do_sample=True,
            eos_token_id=self.tokenizer.eos_token_id,
            pad_token_id=self.tokenizer.pad_token_id
        )
        
        # 4. Extract the response
        # Most tokenizers allow you to split by the prompt itself to get just the new text
        return outputs[0]["generated_text"][len(prompt):].strip()

This class has the generate_answer() method, which takes the question, and the text returned (by the librarian), and returns the answer. Some prompt engineering is involved to make the prompt as specific as possible for the model but at the same time, it is a general wrapper for several questions. Phase 3.1 : Fine Tuning

There are several avenues where we could fine tune this system. They include tuning the chunk size, the overlap window, engineering the prompt, or the number of chunks retrieved. We could also tune the embedding model (the retriever), the re-ranker, or the generator LLM.

  • Training the embeddign model. This involves improving recall @ k, precision of first stage retrieval, robustnuss to paraphased question, and domain specific search quality
  • Training the re-ranker This looks at relevance, rather than just looking at the distance in the vector space.
  • Training the generator LLM Here we train the model things like how to answer using the retrieved context, citing source chunks, refusing when evidence is insufficient, following a desired answer format, synthesizing across multiple chunks.

I’m starting with training the generator first. To do this, we need to create ‘training data’. This would involve a list of queries, the thinking process associated with each query, and their answers. Ideally, it would be created by a panel of experts, but that is a costly endeavor. For this project, I’m making API calls to gemini 2.5 to do this for me. To do this I created a RailDataGenerator class available at https://github.com/jac0bmath3w/rail-safety-ai/blob/main/src/generator.py.

class RailDataGenerator:
    def __init__(self, vault_instance, api_url, api_key):
        self.vault = vault_instance
        self.api_url = api_url #"https://generativelanguage.googleapis.com/v1beta/models/gemini-2.5-flash-preview-09-2025:generateContent"
        self.api_key = api_key

    def _call_teacher(self, system_prompt, user_query):
        payload = {
            "contents": [{"parts": [{"text": user_query}]}],
            "systemInstruction": {"parts": [{"text": system_prompt}]}
        }
        
        # Increased backoff steps to handle stricter 2026 rate limits
        for delay in [2, 4, 8, 16, 32]:
            try:
                # Added a 30s timeout to prevent the script from hanging forever
                response = requests.post(
                    f"{self.api_url}?key={self.api_key}", 
                    json=payload,
                    timeout=30 
                )
                
                if response.status_code == 200:
                    result = response.json()
                    return result.get('candidates', [{}])[0].get('content', {}).get('parts', [{}])[0].get('text', "")
                elif response.status_code == 429:
                    print(f"Rate limit hit. Retrying in {delay}s...")
                else:
                    print(f"Teacher API Error {response.status_code}: {response.text}")
            except requests.exceptions.Timeout:
                print("Request timed out. Retrying...")
            except Exception as e:
                print(f"Request Exception: {e}")
            
            time.sleep(delay)
        return None

    def generate_training_sample(self, chunk_text, file_name, page_num):
        """
        1. Grab a random chunk from the vault.
        2. Ask Teacher to generate a complex question + reasoning process.
        """


        system_prompt = (
            "You are a Senior FRA Rail Safety Expert. Your task is to generate training data "
            "for a student model. Based on the provided manual excerpt, create a challenging "
            "technical question and a perfect response following the 4-Phase Thinking Process.\n\n"
            "PHASE 1: CONTEXTUAL AUDIT\nPHASE 2: EVIDENCE MAPPING\nPHASE 3: SYNTHESIS\nPHASE 4: VERIFICATION\n\n"
            "Output MUST be in valid JSON format: "
            "{'question': '...', 'thinking': '...', 'answer': '...'}"
        )

        user_query = f"MANUAL EXCERPT ({file_name}, Page {page_num}):\n{chunk_text}"
        
        raw_output = self._call_teacher(system_prompt, user_query)
        if not raw_output:
            return None

        # Clean JSON if model included markdown blocks

Any object of this class is initialized with an object to the RailVectorVault. The create_dataset() attribute of this class creates a JSON Lines file. It retrieves random (without replacement) chunks from the vector db, along with its metadata, and passes an engineered system prompt to an API call to gemini (or any other service). Few other ways to generate the training examples might include

  • Self-Instruct, where you take 5-10 human written examples and ask the model to generate similar examples of its own. This can be tricky if the model keeps repeating the same logic over and over.
  • Log-Mining, where you look at the history of how people used the RAG pipeline developed in phase 2, and use the good answers as training data. Here the system must already be in production
  • Data-Augmentation, where you take high quality Q&A pairs and use an LLM to rewrite it in several different ways by changing tone, adding noise, etc.

If using proprietary data, it is imperative to either mask any PII or any information that shouldn’t leave a closed ecosystem or use an offline model to generate these samples. Also, if the training data is 100% AI generated, it cannot be copyrighted. So, it is a good idea to mix in a % of Human in the Loop data while generating this training data.

The training is done in https://github.com/jac0bmath3w/rail-safety-ai/blob/main/notebooks/03_fine_tuning.ipynb. The basic steps involve

  1. loading a pretrained model (Llama-3.2-3B)
  2. attach small trainable adapter layers
  3. train only those adapters (weight matrices of these adapters)
  4. save the newly trained adapters.

I use unsloths FastLanguageModel class for loading and preparing LLM for efficient fine tuning. Unsloth is spcifically meant to reduce memory and make Quantized Low Ranking Adapters (QLoRA) more practical on smaller hardwares. In the from_pretrained() function,the most important parameter would be ‘load_in_4bit’ = True. This compresses the weights of the model agressively, and thus takes less memory on the GPU (with a tradeoff of slightly less numerical precision). This function returns the model (the neural network) and the tokenizer (turns text into tokens).

In the next step we do get_peft_model (PEFT = Parameter Efficient Fine Tuning). This is the step where I turn the base model into a QLoRA fine tuned model. The Parameter Efficient part of PEFT means we do not retrain the large model. Only train the extra small set of weights (Trainable parameters = 24,313,856 of 3,237,063,680 (0.75% trained)). The arguments for this function include

  • r
    This is the LoRA rank. Less the number means less the flexibility of the model. 16 is a balanced choice between lighter models and models that would require much higher memory.
  • target_modules
    This lists out the part of the transformer where the LoRA adapters are inserted. Here I insert adapters in the attention block and the feed forward block.
  • lora_alpha
    Scaling factor for the LoRA update. 16 is commonly used.
  • lora_dropout
    A regularization method. Unsloth recommends 0 for efficiency and speed.
  • bias
    Train the bias or not. Here it is set as False to only train the weights. This is a standard LoRA setting.
  • use_gradient_checkpointing
    Gradient checkpointing saves GPU memory by not storing every intermediate activation during a forward pass.

In the next step, the JSONL file is loaded. This file is structured with 3 columns, ‘question’, ‘thinking’, and ‘answer’. I wrote a function that takes each line and turns it into a conversation string. This is done as the base model is a instruction/chat model. Instead of 3 separate fields, I have one long text field containing the full conversation (stored in the variable messages).

def formatting_prompts_func(examples):
    instructions = examples["question"]
    thoughts = examples["thinking"]
    answers = examples["answer"]
    texts = []

    for instruction, thought, answer in zip(instructions, thoughts, answers):
        # We wrap the thinking and answer together as the 'Assistant' response
        full_response = f"[THINKING PROCESS]\n{thought}\n\n[ANSWER]\n{answer}"

        messages = [
            {"role": "system", "content": "You are a Senior FRA Safety Consultant. Use a 4-Phase Thinking Process."},
            {"role": "user", "content": instruction},
            {"role": "assistant", "content": full_response},
        ]

        text = tokenizer.apply_chat_template(messages, tokenize=False, add_generation_prompt=False)
        texts.append(text)
    return { "text" : texts, }

The function apply_chat_template() takes a structured chat message and convert it into the exact string format expected by the model. tokenize = False returns the response as a string (and not tokens), and add_generation_prompt=False means that no additional text is appended (this is already present in messages). I don’t tokenize and pass the text to the SFTTrainer (specified in the next step). Unsloth uses its specialized fast kernals which handles padding more efficiently than Pytorch.

In the next step, I use the SFTTrainer, and SFTConfig classes from trl (Tranformer Reinforcement Learning) which are high level training helpers. (SFT = Supervised Fine-Tuning). In this step we show the model prompt, and desired response (training data), and teach it to imitate them. The SFTTrainer does

  1. prepare the dataset
  2. tokenizing text
  3. creating batches
  4. runnning the forward pass
  5. calculate loss
  6. backpropagation
  7. update trainiable parameters

SFTConfig stores the configuration settings of the trainer. One important argument is the data_collator. This component takes a list of dataset examples and turns them into one batch. However, the SFTTrainer tokenized the data but also created the text field. This needs to be removed. The DropTextCollator acts as a gatekeeper and throws away the human readable text.

Summary of Lessons Learned

  1. Without RAG, the LLM would depend on the entire context it was trained on, and only know until the training cutoff date. RAG allows us to give the LLM context that it needs to answer questions. Without RAG, an LLM can hallucinate and generate text that looks like what it is supposed to look like.
  2. Tweaking the retriever gives better benefit as if we can’t get the right context to the engine, it will not be able to provide answers
  3. Hybrid search and metadata filtering can be very important for professional applications. Keywords acts as a hard filter,
  4. We can train the engine to reason the way we want it to based on training examples. But fine tuning is for behavior, not facts.
  5. As well as the size of the model, the type of info we feed to the model and the way we feed it in can have an impact.

The transformer has an encoder part as well as a decoder part. But in this project, I'm only interested in the decoder part of the transformer. The steps involved are as follows:

1) We embed the tokens (text being read is broken into tokens). A token could be a word, a part of a word, a special character, etc. Embedding a token means representing a token in a huge dimension. (Say, 512 as given in the paper. It could be more).
2) We add a position component for each token. Otherwise the model doesn't know what token appears where in the string.
3) Attention Block \
  - 3.1 Each token has a query and key vector ($Q$ and $K$ respectively) that is obtained by multiplying the $W_q$ and $W_k$ respectively with the embedding.
  - 3.2 We take the dot product of the $Q$ and $K$ vectors to get a score. If the key of token 1 aligns with the query of token 2, that means the embedding of token 1 "attends" to the embedding of token 2. This results in a large value for the score, essentially meaning token 1 "has something to say about" token 2.
  - 3.3 We divide this by the square root of the dimension of the embedding to prevent the dot product from growing too large.
  - 3.4 We mask the score of future words by setting the value to $-\infty$. This is done so the model doesn't "see the answer." For example, in the string "I read the paper and it was interesting," once we reach "I read the paper," we don't want the model to see the next word. (Note: Masking is not done in an encoder). We use $-\infty$ because the softmax function will then turn that value into $0$.
  - 3.5 We apply the softmax function to get the probabilities.
  - 3.6 We calculate the value vector by multiplying the embedding with $W_v$ (Value weight matrix).
  - 3.7 We calculate the weighted sum of the value vector with the score.
  - 3.8 This is repeated 6 times (according to the original paper), or $n_{layer}$ times sequentially.
4) All the elements in the attention block is repeated in parallel in different heads. We use n_heads parameter to determine how many heads we want. All the results from the n_heads heads is concatenated into one vector. This is multiplied by a final weight matrix to fuse them into a single d_k dimensional vector. 
5) Add & Norm Layer \
  - 5.1 This result is added to the original embedding to get the modified embedding. This is called the 'add layer' or the 'residual connection'
  - 5.2 To keep the activations within a consistent range, we add a norm layer. It could be RMSNorm
6) We have a MLP at the next level where each of the embedding vectors is paralelly processed.
7) We add another Add & Norm layer as described before
8) We add a last linear layer
9) Softmax to get the probability

Note: Since I am not talking about the encoder here, I skipped the cross attention part.

## Other items

### Temperature
This is a parameter you divide the logits by before the softmax in the attention block.
$$
\text{Softmax with Temperature} = \frac{e^{\frac{x_i}{T}}}{\Sigma_{n=0}^{N-1}e^\frac{{x_n}}{T}}
$$

- Low Temp (0.1): Makes the highest probability even higher (very focused).
- High Temp (1.0+): Flattens the distribution (more random/creative).

For FRA manuals, you’ll want a low temperature because you want facts, not "creative" safety rules.

## Ingestion

I create a Class called RailDocumentProcessor. I initialize the class using the splitter tool so that the RecursiveCharacterTextSplitter is just called once when an object of the class is initialized (and not for every document). This tool uses parameters chunk_size = 1000, and chunk_overlap = 150. I used chunk_size of 1000 to not lose context of a specific railway rule. Also use an overlap to ensure that any 'bridge' between chunks is not lost. Also note: 'len' is a built in python function that calculates the length of an object.  Say we were using tokens, we would update 'len' with 'tokenizer.len'. 

Why use RecursiveCharacterTextSplitter as opposed to CharacterTextSplitter? RecursiveCharacterTextSplitter splits text intelligently by natural boundaries (paragraphs, sentences ,spaces) to keep semantic context intact. CharacterTextSplitter splits simply by a fixed character count, which often breaks words and ruins context. 

We use a chunk_size instead of processing the entire document due to context window. LLMs have a limit on how many tokens it can see. The higher the context, the number of parameters that a model has to learn explodes.


This class has the process_directory() method. This goes thru each .pdf file in the directory, extracts texts using the pypdf directory, and then creates chunks and creates chunk using the splitter tool. At the same time it saves metadata for each of the chunk including the source (i.e. the filename), the page number, and the length of character for that chunk. 

```python
import pypdf
import os
from langchain_text_splitters import RecursiveCharacterTextSplitter

class RailDocumentProcessor:
    def __init__(self, chunk_size=1000, chunk_overlap=150):
        self.splitter = RecursiveCharacterTextSplitter(
            chunk_size=chunk_size,
            chunk_overlap=chunk_overlap,
            length_function=len
        )

    def process_directory(self, directory_path):
        """Processes all PDFs and returns a tuple: (list_of_chunks, list_of_metadatas)."""
        all_chunks = []
        all_metadatas = []

        if not os.path.exists(directory_path):
            print(f"Error: Directory {directory_path} not found.")
            return [], []

        for filename in os.listdir(directory_path):
            if filename.endswith(".pdf"):
                print(f"Processing: {filename}")
                path = os.path.join(directory_path, filename)
                
                try:
                    reader = pypdf.PdfReader(path)
                    for i, page in enumerate(reader.pages):
                        page_text = page.extract_text()
                        if not page_text:
                            continue
                        
                        # Create chunks for this specific page
                        page_chunks = self.splitter.split_text(page_text)
                        
                        for chunk in page_chunks:
                            all_chunks.append(chunk)
                            # Enhanced metadata for citations and filtering
                            all_metadatas.append({
                                "source": filename,
                                "page": i + 1,
                                "char_count": len(chunk)
                            })
                except Exception as e:
                    print(f"Could not process {filename}: {e}")
                        
        return all_chunks, all_metadatas
```

For the 5 PDFs, this extracted 2633 chunks. This was surprising to me to see 'only' ~3000 chunks. But $$\text{Total Characters} \approx \text{Chunks} \times \text{Chunk Size}$$  which gives $$3,000 \times 1,000 = 3,000,000 \text{ characters}$$ Even though the 5 PDF files were approximately 25MB, only about 2MB of it is useful text data.

## Embedding

The chunks obtained at the end of the ingestion is sent to the embedder. This is available at [https://github.com/jac0bmath3w/rail-safety-ai/blob/main/src/embed.py](https://github.com/jac0bmath3w/rail-safety-ai/blob/main/src/embed.py)

```python
from sentence_transformers import SentenceTransformer
import torch

class RailEmbedder:
    def __init__(self, model_name='BAAI/bge-base-en-v1.5'):
        # Check if GPU is available
        self.device = 'cuda' if torch.cuda.is_available() else 'cpu'
        print(f"Initializing Embedder on: {self.device}")
        
        self.model = SentenceTransformer(model_name, device=self.device)

    def generate_embeddings(self, text_chunks):
        embeddings = self.model.encode(text_chunks, show_progress_bar=True, convert_to_tensor=False)
        return embeddings
```

For this purpose, I defined a class called RailEmbedder and initialized with the sentence transformers model called 'BAAI/bge-base-en-v1.5'. This is available at [https://huggingface.co/BAAI/bge-base-en-v1.5](https://huggingface.co/BAAI/bge-base-en-v1.5). Other options for the sentence transformer model available include: all-mpnet-base-v2, all-MiniLM-L6-v2 (people on the internet say this is dated and not to use it). 

This class has a method called generate_embeddings(), which takes as argument the text_chunks. This creates an embedding for each chunk in dimensions. A matrix of size 2633x768 (768 is the dimension of the sentence transform model BAAI/bge-base-en-v1.5) is obtaned as a return value of generate_embedding. If GPU is available, it uses that else it uses CPU (much slower). Earlier, I mentioned that each token has a vector embedding. Each token is approximately 4 characters ([source](https://help.openai.com/en/articles/4936856-what-are-tokens-and-how-to-count-them)). So why do we have 2633 vectors at the end of generate_embeddings instead of 2633 (chunks) X 250 (1000 chunk_size / 4 charaacter  per token) X 768? This is because of pooling. What happens during model.encode is

1. Tokenizes the chunk into $N$ tokens.
2. Generates $N$ vectors (one for every token).
3. Collapses those $N$ vectors into one single vector that represents the average meaning of the whole chunk.

What does convert_to_tensor argument in model.encode() do?\

- convert_to_tensor=True: \
  The model returns a PyTorch Tensor. If you are using a GPU, this tensor remains in the VRAM (Video RAM). This is extremely fast if you are immediately passing that data into another neural network layer (like for training).\
- convert_to_tensor=False: \
  The model returns a NumPy array. This data is moved from the GPU back to the System RAM (CPU memory). Vector databases (chromadb is used for this project) expects the data in standard format (NumPy). For storage (which is the next step), I want it to be false.

## Vector Store

This class acts as the "Librarian" of the system, and handles storage, indexing and retrieval. The embeddings generated by RailEmbedder are stored in the disk using this class. I use chromadb library to store these vectors. I created a class RailVectorVault for this purpose available at [https://github.com/jac0bmath3w/rail-safety-ai/blob/main/src/vector_store.py](https://github.com/jac0bmath3w/rail-safety-ai/blob/main/src/vector_store.py). I pass the embedder_instance of class RailEmbedder and create a collection. 

```python
import chromadb

class RailVectorVault:
    def __init__(self, embedder_instance, db_path="./vector_db", collection_name = "rail_safety"):
        # We pass the embedder IN. This is called 'Dependency Injection'.
        self.embedder = embedder_instance 
        self.client = chromadb.PersistentClient(path=db_path)
        self.collection = self.client.get_or_create_collection(name=collection_name)

    def add_documents(self, chunks, metadatas):
        # The Vault asks the Embedder to do its job
        vectors = self.embedder.generate_embeddings(chunks)
        ids = [f"id_{i}" for i in range(len(chunks))]
        
        self.collection.add(
            documents=chunks,
            embeddings=vectors.tolist(),
            metadatas=metadatas,
            ids=ids
        )
    
    def query(self, question, n_results=3):
        """
        Performs a semantic search.
        1. Embeds the question using the injected embedder.
        2. Queries ChromaDB for the closest matches.
        """
        # Embed the query string
        query_vector = self.embedder.generate_embeddings([question])
        
        # Search the collection
        results = self.collection.query(
            query_embeddings=query_vector.tolist(),
            n_results=n_results
        )
        return results  
```

The method add_documents() takes the chunks, embeddings, and the metadata and stores it in drive. The method query 1. Turns the question into a vector. 2. Finds the $n_results$ most similar chunks. 3. Returns a dictionary containing the text and the metadata.


# Phase 2: RAG Pipeline

## The Reasoning Engine

I defined the class RailSafetyEngine which serves as the reasoning brain of the RAG system. When you query the vector database, it returns n_results number of text that closely match the embeddings that we stored in the database. Think of it as the librarian returning the relevant books that you need to answer the query. Then the brain processes them to return the answer to the question. I use the following imports from the transformers library

1. AutoModelForCausalLM
   - A class that loads the correct model architecture based on the model that you pass (example llama or gemma)
2. AutoTokenizer
   - Handles the translation between human text and numerical values that are fed to a machine. 
3. pipeline
   - Wrapper for the tokenization, model execution, and decoding into one function call. 
4. BitsAndByesConfig
   - This helps to compress the model so that it fits in the T4 GPU memory (used in colab).


When this class is initialzed, the device is mapped (cpu or gpu), the quantization is set up (bnb_config), loads the model (using scaled dot product attention implementation, shortened as sdpa), and creates the pipeline. 'sdpa' and 4-bit quantization are the "Optimization Duo" that allows a model meant for a $20,000 server to run on a free Google Colab instance.

```python
from transformers import AutoModelForCausalLM, AutoTokenizer, pipeline, BitsAndBytesConfig
import torch

class RailSafetyEngine:
    def __init__(self, model_id="unsloth/Llama-3.2-3B-Instruct"):
        self.device = "cuda" if torch.cuda.is_available() else "cpu"
        self.tokenizer = AutoTokenizer.from_pretrained(model_id)
        
        # Ensure a padding token exists
        if self.tokenizer.pad_token is None:
            self.tokenizer.pad_token = self.tokenizer.eos_token
        
        bnb_config = BitsAndBytesConfig(
            load_in_4bit=True,
            bnb_4bit_use_double_quant=True,
            bnb_4bit_quant_type="nf4",
            bnb_4bit_compute_dtype=torch.bfloat16
        )
        
        self.model = AutoModelForCausalLM.from_pretrained(
            model_id,
            quantization_config=bnb_config,
            device_map="auto",
            attn_implementation="sdpa"
        )
        
        self.pipe = pipeline(
            "text-generation",
            model=self.model,
            tokenizer=self.tokenizer,
            max_new_tokens=512,
            temperature=0.1, 
            device_map="auto"
        )

    def generate_answer(self, question, context_chunks):
        if not context_chunks:
            return "No relevant safety manual excerpts were found."

        context_text = "\n\n".join(context_chunks)
        
        # 1. Structure the data as a standard list of messages
        messages = [
            {
                "role": "system", 
                "content": "You are a Senior FRA Safety Consultant. Use ONLY the provided context. Cite Page numbers."
            },
            {
                "role": "user", 
                "content": f"CONTEXT:\n{context_text}\n\nQUESTION: {question}"
            }
        ]
        
        # 2. Use the model-agnostic chat template
        # tokenize=False returns a string; add_generation_prompt=True adds the 'assistant' header
        prompt = self.tokenizer.apply_chat_template(
            messages, 
            tokenize=False, 
            add_generation_prompt=True
        )
        
        # 3. Generate
        outputs = self.pipe(
            prompt, 
            do_sample=True,
            eos_token_id=self.tokenizer.eos_token_id,
            pad_token_id=self.tokenizer.pad_token_id
        )
        
        # 4. Extract the response
        # Most tokenizers allow you to split by the prompt itself to get just the new text
        return outputs[0]["generated_text"][len(prompt):].strip()
```

This class has the generate_answer() method, which takes the question, and the text returned (by the librarian), and returns the answer. # Phase 3.1 : Fine Tuning

There are several avenues where we could fine tune this system. They include tuning the chunk size, the overlap window, engineering the prompt, or the number of chunks retrieved. We could also tune the embedding model (the retriever), the re-ranker, or the generator LLM.

- Training the embeddign model.
  This involves improving recall @ k, precision of first stage retrieval, robustnuss to paraphased question, and domain specific search quality
- Training the re-ranker
  This looks at relevance, rather than just looking at the distance in the vector space.
- Training the generator LLM
  Here we train the model things like how to answer using the retrieved context, citing source chunks, refusing when evidence is insufficient, following a desired answer format, synthesizing across multiple chunks.

I'm starting with training the generator first. To do this, we need to create 'training data'. This would involve a list of queries, the thinking process associated with each query, and their answers. Ideally, it would be created by a panel of experts, but that is a costly endeavor.     def _call_teacher(self, system_prompt, user_query):
        payload = {
            "contents": [{"parts": [{"text": user_query}]}],
            "systemInstruction": {"parts": [{"text": system_prompt}]}
        }
        
        # Increased backoff steps to handle stricter 2026 rate limits
        for delay in [2, 4, 8, 16, 32]:
            try:
                # Added a 30s timeout to prevent the script from hanging forever
                response = requests.post(
                    f"{self.api_url}?key={self.api_key}",

                    timeout=30

                    result = response.json()
                    return result.get('candidates', [{}])[0].get('content', {}).get('parts', [{}])[0].get('text', "")

The training is done in [https://github.com/jac0bmath3w/rail-safety-ai/blob/main/notebooks/03_fine_tuning.ipynb](https://github.com/jac0bmath3w/rail-safety-ai/blob/main/notebooks/03_fine_tuning.ipynb). The basic steps involve

1. loading a pretrained model (Llama-3.2-3B)
2. attach small trainable adapter layers
3. train only those adapters (weight matrices of these adapters)
4. save the newly trained adapters.

I use unsloths FastLanguageModel class for loading and preparing LLM for efficient fine tuning. Unsloth is spcifically meant to reduce memory and make Quantized Low Ranking Adapters (QLoRA) more practical on smaller hardwares. In the from_pretrained() function,the most important parameter would be 'load_in_4bit' = True. This compresses the weights of the model agressively, and thus takes less memory on the GPU (with a tradeoff of slightly less numerical precision). This function returns the model (the neural network) and the tokenizer (turns text into tokens).

In the next step we do get_peft_model (PEFT = Parameter Efficient Fine Tuning). This is the step where I turn the base model into a QLoRA fine tuned model. The Parameter Efficient part of PEFT means we do not retrain the large model. Only train the extra small set of weights (Trainable parameters = 24,313,856 of 3,237,063,680 (0.75% trained)). The arguments for this function include

- r \
  This is the LoRA rank. Less the number means less the flexibility of the model. 16 is a balanced choice between lighter models and models that would require much higher memory.
- target_modules \
  This lists out the part of the transformer where the LoRA adapters are inserted. Here I insert adapters in the attention block and the feed forward block. 
- lora_alpha \
  Scaling factor for the LoRA update. 16 is commonly used.
- lora_dropout \
  A regularization method. Unsloth recommends 0 for efficiency and speed.
- bias \
  Train the bias or not. Here it is set as False to only train the weights. This is a standard LoRA setting.
- [use_gradient_checkpointing]{style="color: red;"} \
  Gradient checkpointing saves GPU memory by not storing every intermediate activation during a forward pass.


In the next step, the JSONL file is loaded. This file is structured with 3 columns, 'question', 'thinking', and 'answer'. I wrote a function that takes each line and turns it into a conversation string. This is done as the base model is a instruction/chat model. Instead of 3 separate fields, I have one long text field containing the full conversation (stored in the variable messages). 

```python
def formatting_prompts_func(examples):
    instructions = examples["question"]
    thoughts = examples["thinking"]
    answers = examples["answer"]
    texts = []

    for instruction, thought, answer in zip(instructions, thoughts, answers):
        # We wrap the thinking and answer together as the 'Assistant' response
        full_response = f"[THINKING PROCESS]\n{thought}\n\n[ANSWER]\n{answer}"

        messages = [
            {"role": "system", "content": "You are a Senior FRA Safety Consultant. Use a 4-Phase Thinking Process."},
            {"role": "user", "content": instruction},
            {"role": "assistant", "content": full_response},
        ]

        text = tokenizer.apply_chat_template(messages, tokenize=False, add_generation_prompt=False)
        texts.append(text)
    return { "text" : texts, }
```

The function apply_chat_template() takes a structured chat message and convert it into the exact string format expected by the model. tokenize = False returns the response as a string (and not tokens), and add_generation_prompt=False means that no additional text is appended (this is already present in messages). I don't tokenize and pass the text to the SFTTrainer (specified in the next step). Unsloth uses its specialized fast kernals which handles padding more efficiently than Pytorch. 

In the next step, I use the SFTTrainer, and SFTConfig classes from trl (Tranformer Reinforcement Learning) which are high level training helpers. (SFT = Supervised Fine-Tuning). In this step we show the model prompt, and desired response (training data), and teach it to imitate them. The SFTTrainer does

1. prepare the dataset
2. tokenizing text
3. creating batches
4. runnning the forward pass
5. calculate loss
6. backpropagation
7. update trainiable parameters

SFTConfig stores the configuration settings of the trainer. One important argument is the data_collator. This component takes a list of dataset examples and turns them into one batch. However, the SFTTrainer tokenized the data but also created the text field. This needs to be removed. The DropTextCollator acts as a gatekeeper and throws away the human readable text.

### The Metrics
- Hit@1 : This is the most critical metric. It tells you how often the very first result was the correct chunk. At 0.467, the Reranker is getting the exact right page nearly 47% of the time.
- Hit@3 / Hit@5 : These tell you how often the correct answer was "in the top 3" or "in the top 5." The Reranker has a 72.4% Hit@5. This means that if you feed 5 chunks to the LLM, it has the "truth" in front of it 72% of the time.
- MRR (Mean Reciprocal Rank): This is the average of $1 / \text{Rank}$. If the answer is at #1, you get 1.0.If it's at #2, you get 0.5. The Reranker MRR of 0.567 means that, on average, the correct answer is sitting between Rank 1 and Rank 2.

# Summary of Lessons Learned

1. Without RAG, the LLM would depend on the entire context it was trained on, and only know until the training cutoff date. RAG allows us to give the LLM context that it needs to answer questions. Without RAG, an LLM can hallucinate and generate text that looks like what it is supposed to look like. 
2. Tweaking the retriever gives better benefit as if we can't get the right context to the engine, it will not be able to provide answers
3. Hybrid search and metadata filtering can be very important for professional applications. Keywords acts as a hard filter, 
4. We can train the engine to reason the way we want it to based on training examples. But fine tuning is for behavior, not facts. 
5. As well as the size of the model, the type of info we feed to the model and the way we feed it in can have an impact.
